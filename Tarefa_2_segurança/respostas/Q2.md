# Q2 — Ataque Prático: Roubo de Token via XSS

## a) O que acontece

1. O atacante consegue inserir o comentário malicioso no produto.
2. O comentário contém um elemento `<img>` com uma URL inválida (`x`).
3. O navegador tenta carregar a imagem.
4. O carregamento falha e dispara o evento `onerror`.
5. O JavaScript do `onerror` é executado porque o frontend utiliza `dangerouslySetInnerHTML` sem sanitização (V15).
6. O código acessa `localStorage.getItem('token')`.
7. Como o JWT está armazenado em `localStorage` (V12), o script consegue lê-lo.
8. O token é enviado para o domínio controlado pelo atacante por meio de uma requisição para `evil.com`.
9. O atacante passa a possuir uma credencial que pode ser reutilizada contra a API.

## b) Por que o ataque ao endpoint administrativo funciona?

A vulnerabilidade V10 permite acessar `/api/admin/orders` sem uma verificação real de role no servidor. A informação de `role` armazenada em `localStorage` (V13) também não constitui controle de acesso confiável.

Portanto, mesmo que a interface tenha sido originalmente apresentada a um usuário comum, o backend aceita o token como autenticação e não verifica se o usuário possui a role `admin`. O atacante utiliza o token roubado diretamente na requisição HTTP e acessa os pedidos administrativos.

A correção é fazer a autorização no servidor, como em Q5, usando middleware `requireRole('admin')`.

## c) Cookie HttpOnly

Se o access token estiver em um cookie `HttpOnly`, JavaScript executado no navegador não consegue ler o valor do cookie por meio de `document.cookie` nem por acesso equivalente ao `localStorage`.

Assim, o XSS ainda seria uma vulnerabilidade e poderia realizar ações em nome da vítima em determinados cenários, mas o mecanismo específico de **roubo direto do token pelo JavaScript** seria dificultado. Por isso, `HttpOnly` reduz o impacto de XSS sobre o segredo do token, mas não substitui a prevenção de XSS.
