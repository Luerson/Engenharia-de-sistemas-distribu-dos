# Q3 — Ataque Prático: SQL Injection

## a) Login

Com o email:

```text
' OR '1'='1' --
```

a consulta original:

```sql
SELECT * FROM users WHERE email = '${email}'
AND password = '${password}'
```

pode resultar, considerando uma senha qualquer, em uma estrutura equivalente a:

```sql
SELECT * FROM users
WHERE email = '' OR '1'='1' --'
AND password = 'qualquer_senha'
```

O trecho `'1'='1'` é sempre verdadeiro e `--` inicia um comentário no restante da linha em SQL compatível com essa sintaxe. Assim, a condição de senha deixa de cumprir sua função original e a consulta pode retornar um usuário.

A correção é utilizar parâmetros, por exemplo:

```sql
SELECT id, email, password_hash, role
FROM users
WHERE email = $1
```

e comparar a senha separadamente com `bcrypt.compare()`.

## b) SQL Injection em pedidos

O ID:

```text
1 UNION SELECT id, email, password, role, NULL, NULL FROM users --
```

é interpretado como parte da instrução SQL porque V6 concatena diretamente `req.params.id`.

O `UNION SELECT` pode fazer a consulta retornar dados da tabela `users`, incluindo identificadores, emails, hashes/senhas armazenadas e roles, dependendo da estrutura exata do banco.

Isso é possível mesmo autenticado porque **autenticação não elimina SQL Injection**. O atacante possui uma sessão válida, mas consegue manipular a consulta executada pelo servidor.

A correção é utilizar query parametrizada:

```sql
SELECT *
FROM orders
WHERE id = $1
```

## c) Relação com V1

O segredo JWT hardcoded de V1 não é necessário para executar o SQL Injection. Entretanto, se um atacante também obtiver o segredo usado para assinar JWTs, ele pode potencialmente fabricar tokens válidos com claims escolhidas pelo próprio atacante.

Assim, V1 pode aumentar muito o impacto de uma combinação de falhas: SQL Injection pode expor dados e, separadamente, o segredo JWT exposto pode permitir falsificação de tokens. A defesa deve corrigir ambas as vulnerabilidades.
